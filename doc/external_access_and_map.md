# 外部稳定访问与地图显示方案

本文档记录当前 Demo 对外访问和地图页稳定性的推荐方案。

## 当前问题判断

本地访问正常，但通过 Cloudflare 临时隧道访问时出现慢、打不开或地图空白，通常由三类原因造成：

- Cloudflare Quick Tunnel 是临时隧道，域名随机、链路质量不稳定，更适合演示，不适合长期对外访问。
- 原地图页依赖外部 CDN 和第三方 GeoJSON，公网访问时这些资源可能加载慢、被拦截或超时。
- 生成报告和智能问答会调用大模型与 embedding 服务，外网用户访问时会叠加本机上传、隧道转发、模型接口响应三段延迟。

## 已做的地图修复

地图页已改为本地渲染组件：

- 不再加载 `cdn.jsdelivr.net` 的 ECharts。
- 不再请求 `geo.datav.aliyun.com` 的地图 GeoJSON。
- 页面只请求本项目自己的 `/api/map/overview` 接口。
- 当前以苏州 Demo 为核心展示城市诉求规模、回复效率和热点问题。

这样通过 Cloudflare、内网穿透或局域网访问时，地图不会因为第三方地图资源失败而空白。

## 推荐方案一：Cloudflare Named Tunnel

如果目标是“继续放在自己电脑上，但希望外部稳定访问”，推荐使用 Cloudflare Named Tunnel，而不是 Quick Tunnel。

特点：

- 域名固定，可绑定自己的域名，例如 `appeal.example.com`。
- 可把 `cloudflared` 安装成 Windows 服务，开机自动运行。
- 不需要在路由器上开放公网端口。
- 可以接入 Cloudflare Access，给外部访问加登录鉴权。

适合：阶段性演示、小范围给领导或同事查看、仍希望由本机承载应用。

建议配置：

1. 准备一个域名并接入 Cloudflare。
2. 在本机登录 `cloudflared`。
3. 创建 named tunnel。
4. 配置 hostname 指向本地 `http://localhost:8000`。
5. 安装为 Windows service。
6. 给公开页面加访问控制，避免 API Key 或内部数据被无授权访问。

## 推荐方案二：VPS + 反向代理

如果目标是“更稳定、更像正式系统”，建议部署到云服务器或 VPS。

结构：

- Nginx/Caddy 负责 HTTPS 和反向代理。
- FastAPI 使用 Uvicorn/Gunicorn 运行。
- SQLite 可先继续使用，后续升级 PostgreSQL。
- 静态文件和文档由服务端直接托管。

优点：访问速度和稳定性明显好于家用电脑 + 临时隧道。缺点是需要购买服务器并做基础运维。

## 推荐方案三：FRP + VPS

如果必须运行在本机，但希望入口更稳定，可以购买一台轻量 VPS，把 VPS 作为固定入口，用 FRP 将请求转发到本机。

适合：本机有大数据或本地资源必须保留，不方便全部迁移到服务器。

缺点：需要维护 VPS 和 FRP 服务，配置复杂度高于 Cloudflare Named Tunnel。

## 不太推荐：路由器端口映射

直接把本机 8000 端口通过路由器暴露到公网不推荐：

- 家庭宽带公网 IP 不稳定，很多运营商没有公网 IPv4。
- 安全风险高，需要额外处理 HTTPS、防火墙、鉴权、日志和限流。
- 一旦程序暴露未授权接口，风险会直接落到本机。

## 当前阶段建议

短期演示：使用 Cloudflare Named Tunnel + 固定域名 + Access 鉴权。

中期稳定展示：迁移到云服务器，保留本机作为开发环境。

正式产品化：前后端、数据库、向量库、任务队列和模型网关拆分部署，并加权限、日志、审计和缓存。

## 性能优化建议

- 报告生成、问答生成做异步任务，前端轮询任务状态。
- 对同一问题和同一报告模板做结果缓存。
- embedding 检索结果缓存到数据库，减少重复调用。
- 首页、地图页、仪表盘尽量只读取本地数据库，不触发模型调用。
- 对公网访问开启 gzip/br 压缩和静态资源缓存。
